# 《恶魔与精灵》R12：满电脑队友卡顿、发热检查与优化报告（R12-PF2）

2026-11-25 · 底稿：11-24 交接站「操作提示」版，开发客户端 `6cfa42d`（源码清单 SHA-256 `6cfa42d6…2a383a22`，1,460 个文件，已逐个核对一致）。它是在上次的 COW8D-PF1 上加了操作提示等功能，PF1 的性能修改都还在。

> 所有数字都来自这台 Mac（Apple M6）。iPhone 12 会慢很多（估计 2.5–4 倍），**只能当前后对比看，不能当真机验收**。真机上是否稳 60 帧、不发热，要按第 6 节在手机上确认。

## 1. 结论先说

1. **iPhone 上的瓶颈很可能是“画布用 CPU 绘制”。** 我在这台 Mac 上用和微信 iOS 高性能模式同一个 WebKit 引擎跑了游戏：
   - 画布用显卡画时，后期混战每帧只要约 1–1.6 ms。照这个速度，iPhone 不可能只有 40 帧。
   - 关掉显卡加速、改用 CPU 画（CoreGraphics）时，同样的画面每帧要 5–6.5 ms。乘以 iPhone 12 的倍数是 13–20 ms 以上，正好对上你真机上「后期战斗 38–43 帧」「越玩越烫」的记录。
   
   所以本轮按「CPU 画布」来找开销。这种模式下最贵的是：
   - 全屏半透明纯色填充（每次约 1.5 ms）；
   - 文字和矢量图形；
   - 镜头快速移动时现画地形。
2. **后期逻辑**：小恶魔围攻城墙时，要反复检测「这条线有没有被地形挡住」，是后期逻辑的大头（约占逻辑时间 28–37%）。本轮在**结果完全不变**的前提下，砍掉了其中大约 4 成的无效检测。
3. **新加的「单人切镜」**：第 60 秒左右恶魔苏醒时，镜头会自己飞到 3,600 单位外再飞回，原版一路现画地形，连续长帧。已改成按镜头移动方向提前画好。
4. **改了 3 处 + 版本标签，玩法和画面不变**。证明方法：同一局用「游戏时钟」重放，原版和修改版 12 分钟后的完整状态一模一样；逐帧比较整屏像素 900 帧全部一致（第 4 节）。
5. **还没解决的**（第 5 节，有几项要你拍板）：
   - CPU 画布下绘制仍是大头，每帧约 5 ms（M6）。
   - 准备期全屏浅蓝和「城墙被毁救援」全屏暗色遮罩，每帧各多 1.5–2.3 ms。
   - 一种更快的镜头移动（1 秒 4,000 单位）仍会顿一下。

## 2. 怎么查的

| 测试环境 | 用途 |
|---|---|
| Node + Skia（上次的工具） | 逐帧耗时、CPU 采样、逐秒状态和逐帧像素回归 |
| **WebKit 测试环境（本轮新做）** | 用 macOS 的 WKWebView 跑完整游戏，微信 iOS 高性能模式用的就是 WKWebView。可以切换「画布用显卡画 / 用 CPU 画」，按绘制阶段或逐次绘制调用计时，并统计 WebKit 绘制进程、网页进程的 CPU 时间 |
| 场景 | 8 个电脑队友、疯狂难度、精灵不死、镜头自动看「画面里单位最多的地方」（模拟满电脑队友混战），以及 12 分钟整局、第 60 秒切镜、第 17–21 波后期混战 |

另外，**测试环境本身修了一个大坑**：游戏里第 20 波石头人等 Boss 要等素材异步加载完才出场。原来的测试宿主里，加载完成的时刻取决于机器当时的忙闲，同样操作跑两次局面会分叉，看起来像「改动改变了玩法」。现在测试宿主里的定时器按游戏时钟走，图片加载完成的通知在固定帧发出，同样输入必定得到同样结果。原版连跑两次、和修改版各一次，12 分钟后状态指纹都是 `c4eb4738…`。以后 Codex 做对比也应该用这个模式（`VTIMERS=1`，见测试工具 README）。

- 代码里每处都有 `PERF-` 注释。

| 代码 | 文件 | 改了什么 | 画面/玩法 |
|---|---|---|---|
| M1 | `network/mini-demon-follow.js` | 小恶魔找攻击站位时，「被地形挡住」只会让代价 +70。先算其余部分，如果已经不可能比当前最优点更好，就不做那次视线检测。顺序、加法、严格比较都不变 | 选出的位置完全一样 |
| M2 | 同上 | 小恶魔绕开同伴的路径搜索（Dijkstra）：先看这条边能不能让到达代价变小，不能就不做两项通行检测 | 路线完全一样 |
| L4 | `art163/terrain-edge-prefetch.js`（在 art163 分包里） | 镜头移动超过步行速度时（切镜、首次遭攻击聚焦、回基地、拖地图），按移动方向找出 0.5 秒内会进入画面的地形块，最早进入的先画。每帧最多 2 块，而且只在本帧地形耗时不到 4 ms 时才画。慢速移动保持 PF1 的做法 | 每块地形的绘制操作不变，像素一样 |
| 标签 | `single-player-build.js`、`asset-config.js`、`release.json` | 首页左上角改为「R12-PF2-CLAUDE · 单人测试 · …」；诊断版本号末尾加 `-PF2`，只改文字 | 只有首页那行字 |

**包大小**：交接说明里预览主包只剩 1,732 字节余量。本次主包净增约 100 字节，主包里的说明注释已经压到最短，详细说明在这份报告里。地形预取文件在 art163 分包里，比原版多 2.7 KB（R12 预览总包是 31,457,909 字节）。实际预览包大小以开发者工具显示为准。

## 5. 还没解决的，以及需要你决定的

**1）绘制仍是大头。** CPU 画布模式下，后期混战每帧约 5 ms（M6），按 iPhone 12 估算仍在 12–15 ms 左右，留给发热降频的余量不多。主要构成（M6，CPU 画布）：

| 项目 | 每帧 |
|---|---|
| 城墙被毁救援提示的全屏暗色遮罩（出现时） | 1.5–2.3 ms |
| 准备期（每局前 60 秒）全屏浅蓝色 | 约 1.6 ms |
| 准备期跳动的倒计时描边文字 | 约 0.1–0.2 ms |
| 建筑层 | 约 0.86 ms |
| 顶部界面 | 约 0.67 ms |
| 地形 | 约 0.33 ms |
| 树/矿层 | 约 0.31 ms |
| 单位和特效合计 | 约 1 ms |

**2）全屏半透明遮罩可以快 5 倍，但要你拍板。** 做法是把「每帧铺一层半透明颜色」换成「贴一张同色的整屏图」。实测结果：
- CPU 画布下：像素逐个完全一样，每次 1.5 ms → 0.31 ms。
- 画布用显卡画时：两种画法会有 1–4 级的色值差（肉眼看不出），而且不会更快。
- 内存：遮罩显示期间要多占约 5 MB。

可以加一个开机时的小测速，只在 CPU 画布的手机上启用，这样显卡画布的手机画面不变。要不要做，你定。

**3）更快的那种镜头移动仍会顿一下。** 原因是地形缓存只有 16 MB（约 59 块），容不下「出发点一屏 + 路上 + 目的地」，飞回时只能现画。两条路：
- 镜头场景期间临时多给地形缓存约 8 MB；
- 把这种镜头放慢一点，但这会改变镜头表现。

都需要你同意。

**4）高性能模式要在手机上确认真的生效。** 你之前的记录是：
- 开高性能：「流畅了」；
- 关掉：「巨卡发烫」。

游戏开局会把实际模式记进诊断记录（`runtime-mode` 事件里的 `highPerformance`）。真机测试时请先确认它是 `true`；如果是 `false` 或空，后面的优化都不顶用。

**5）测试码。** 微信开发者工具的「服务端口」还是关闭状态。这是安全设置，我不会替你打开。可以：
- 你打开「设置 › 安全设置 › 服务端口」，我来出码；
- 或者你在开发者工具里导入 `恶魔与精灵_R12-PF2优化/client`，直接点「预览」。

## 6. 真机验收怎么做

同一台 iPhone 12，同样亮度和电量区间，分别用 R12 原版和 R12-PF2 测：
1. 单人、8 个电脑队友、疯狂难度，各玩 30 分钟。
2. 记录左上角 FPS、明显顿卡的时间点、机身温度、耗电。
3. 记录内存警告次数（诊断记录里的 `memory` 事件）。
4. 重点看第 60 秒恶魔苏醒切镜，以及第 15 波以后小恶魔围攻城墙的时段。

没在真机上测过的指标，我不会说已经达标。
