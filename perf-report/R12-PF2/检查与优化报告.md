# 《恶魔与精灵》R12：满电脑队友卡顿、发热检查与优化报告（R12-PF2）

2026-11-25 · 底稿：11-24 交接站「操作提示」版，开发客户端 `6cfa42d`（源码清单 SHA-256 `6cfa42d6…2a383a22`，1,460 个文件，已逐个核对一致）。它是在上次的 COW8D-PF1 上加了操作提示等功能，PF1 的性能修改都还在。

11-25 晚更新：按你的决定（「做，只在CPU画布启用」）加了全屏半透明遮罩提速 PERF-T1，见 3、4.5 节。

> 所有数字都来自这台 Mac（Apple M6）。iPhone 12 会慢很多（估计 2.5–4 倍），**只能当前后对比看，不能当真机验收**。真机上是否稳 60 帧、不发热，要按第 6 节在手机上确认。

## 1. 结论先说

1. **iPhone 上的瓶颈很可能是“画布用 CPU 绘制”。** 我在这台 Mac 上用和微信 iOS 高性能模式同一个 WebKit 引擎跑了游戏：
   - 画布用显卡画时，后期混战每帧只要约 1–1.6 ms。照这个速度，iPhone 不可能只有 40 帧。
   - 关掉显卡加速、改用 CPU 画（CoreGraphics）时，同样的画面每帧要 5–6.5 ms。乘以 iPhone 12 的倍数是 13–20 ms 以上，正好对上你真机上「后期战斗 38–43 帧」「越玩越烫」的记录。
   
   所以本轮按「CPU 画布」来找开销。这种模式下最贵的是：
   - 全屏半透明纯色填充（每次约 1.5 ms）；
   - 文字和矢量图形；
   - 镜头快速移动时现画地形。
2. **后期逻辑**：小恶魔围攻城墙时，要反复检测「这条线有没有被地形挡住」，是后期逻辑的大头（约占逻辑时间 28–37%）。本轮在**结果完全不变**的前提下，砍掉了其中大约 4 成的无效检测。
3. **新加的「单人切镜」**：第 60 秒左右恶魔苏醒时，镜头会自己飞到 3,600 单位外再飞回，原版一路现画地形，连续长帧。已改成按镜头移动方向提前画好。
4. **全屏半透明遮罩（11-25 晚加）**：准备期浅蓝、救援提示、菜单和面板底色共 10 处，在 CPU 画布的手机上改为贴一张同色整屏图。这台 Mac 上准备期每帧 5.81 → 5.13 ms，开升级面板时 4.61 → 3.67 ms。开机时先检测，同时满足两条才启用：画布是 CPU 画的；两种画法逐像素相同。显卡画布的手机不启用，画法和原版一样。
5. **改了 4 处 + 版本标签，玩法完全不变**。同一局用「游戏时钟」重放，原版和修改版 12 分钟后的完整状态一模一样。画面：
   - M1、M2、遮罩（T1）和标签：所有逐帧对比都一致（4.4、4.5 节）。
   - **更正**：上一版报告说 L4 画面也完全一致，不完整。11-25 晚在 WebKit 里换了一种开局时机（先在首页停 1 秒）再比，第 65 秒以后有些树的像素和原版有轻微差别。位置没变，每个像素平均差 3–4 级，放大对比也看不出来。原因是 L4 改变了切镜时地形缓存的绘制时机（4.4 节）。要不要保留 L4，请你定（第 5 节第 3 条）。
6. **还没解决的**（第 5 节，有几项要你拍板）：
   - CPU 画布下绘制仍是大头，每帧约 5 ms（M6）。
   - 一种更快的镜头移动（1 秒 4,000 单位）仍会顿一下。

| 测试环境 | 用途 |

另外，**测试环境本身修了一个大坑**：游戏里第 20 波石头人等 Boss 要等素材异步加载完才出场。原来的测试宿主里，加载完成的时刻取决于机器当时的忙闲，同样操作跑两次局面会分叉，看起来像「改动改变了玩法」。现在测试宿主里的定时器按游戏时钟走，图片加载完成的通知在固定帧发出，同样输入必定得到同样结果。原版连跑两次、和修改版各一次，12 分钟后状态指纹都是 `c4eb4738…`。以后 Codex 做对比也应该用这个模式（`VTIMERS=1`，见测试工具 README）。

### 4.4 正确性

- 逐帧回归，确定性模式、8 电脑、疯狂难度：
  - 脚本操作 2 分钟（走路、跳镜头、切后台）：120 个逐秒状态、90 帧整屏像素全部一致；最终版本又复跑了一次，仍然一致。
  - 镜头跟随混战 6 分钟：360 个逐秒状态，每 30 帧比一次整屏像素，共 810 帧，全部一致。
- 随机乱点试玩：3 个种子 × 15,000 帧，0 个异常。另外有 1–2 次「循环暂停超过 1.5 秒」，帧位置和长度与原版完全相同，属于原版就有的菜单暂停行为。
- **WebKit 逐帧对比（11-25 晚补测，发现 L4 有像素差别）。** 条件：CPU 画布，确定性模式，8 电脑、疯狂难度，90 秒，有菜单开关；每 30 帧和每次菜单开关比一次整屏像素，共 234 帧。
  - 直接开局：PF2 与原版 234 帧全部一致，只加 L4 时也一致。
  - 开局前先在首页停 1 秒（真机上总会在首页停一会儿），逐项对比：

    | 和原版比 | 不同的帧 | 游戏状态 |
    |---|---|---|
    | 原版复跑 | 0 | 一致 |
    | 只改版本标签 | 0 | 一致 |
    | 只改 M1、M2 | 0 | 一致 |
    | **只加 L4** | **66 帧（第 65 秒以后比的帧全部不同）** | 一致 |
    | PF2 全部 | 同上 66 帧 | 一致 |

  - 差别在哪：第 65 秒，屏幕上方 3 棵树；第 75 秒左侧一片树；第 90 秒约占整屏 7% 的像素。树的位置没有变，每个像素平均差 3–4 级，大部分差 15 级以内，少数轮廓像素差得多。放大并排看不出区别，见 `报告/R12数据/L4-树像素差-第65秒-左原版中PF2右差异.png`。
  - 原因：第 60–65 秒恶魔苏醒切镜时，L4 提前画地形块，切镜期间地形缓存的绘制时机和顺序都变了。之后有些树画出来的像素，和原版那边的缓存历史不同，就有细微差别。具体是哪一层缓存，我还没追到。原版自己每帧画几块地形，在真机上要看真实耗时（每帧最多 2 块、2 ms 以内），所以原版在不同手机、不同次运行之间，大概率也有同类细微差别。这一点是推断，没有验证。
  - 显卡画布下，这个测试工具连原版自己都不能稳定复现（不同时间跑同一版本，画面可能全部不同），所以这项对比只在 CPU 画布下做。

### 4.5 全屏半透明遮罩（PERF-T1，11-25 加）

你定的是「做，只在 CPU 画布启用」。做法：

1. **改了哪些地方。** 一共 10 处遮罩。它们原来每帧都在整个屏幕上铺一层半透明纯色，现在改为先问一下 `screenTintBN`：
   - 遮罩：准备期浅蓝、城墙被毁救援、建造菜单、升级面板、遗物、队友数据、恶魔面板、暂停菜单、存档、队友经济（2 处同色）；
   - 允许贴图时：贴一张事先铺好同色的整屏图；
   - 不允许时：照原样填充，和原版逐条绘制指令相同。
   
   颜色会随时间变化的几处没有动：进化闪光、胜利和结算画面。
2. **开机检测，每台手机只测一次。** 检测在首页或加载画面里分 15 帧做完，约 0.25 秒；对局开始前，这些帧每帧只多花几毫秒。两项都满足才启用贴图：
   - **CPU 画布的特征**：在 1024×512 的测试画布上，铺色明显比贴图慢（至少 4 ms、且至少 2 倍）。用显卡画的画布两者差不多快。计时前先等之前排队的绘制画完，不把游戏自己的绘制算进去。
   - **逐像素核对**：10 种遮罩颜色逐一核对。每种颜色都在一条覆盖 0–255 全部色值（含半透明底色）的色带上，各用两种画法画一遍，读回像素比较，必须完全相同。只要有一种颜色不同，就整台手机不启用。
   - 不在这 10 种里的颜色、画布有缩放或旋转、透明度或混合方式不是默认值、出现任何报错：一律照原样填充。
3. **内存**：
   - 整屏图约 5.3 MB（780×1688），只在遮罩显示期间存在，最后一次使用 3 秒后释放；
   - 检测用的两块测试画布共 4 MB，检测结束即丢弃。

**验证**

| 项目 | 结果 |
|---|---|
| 检测独立测试（WebKit，真实时钟） | CPU 画布：10 次全部判为启用。显卡画布：20 次全部不启用。另外故意把计时做成「看起来是 CPU 画布」，显卡画布 3 次都被像素核对拦下，原因是第 1 种颜色就有 1–4 级色差 |
| 游戏里走一遍检测（WebKit、CPU 画布、确定性模式、首页停 1 秒、检测用真实时钟） | 判为 CPU 画布，10 种颜色全部通过；准备期 3,609 次、建造菜单 540 次、升级面板 540 次、暂停菜单 2 次，全部走贴图 |
| 像素：贴图 vs 原画法（同一版本，WebKit、CPU 画布） | 首页停 1 秒的一局：真实检测（启用贴图）、强制贴图、强制原画法三局，234 帧整屏像素全部相同。不停首页的一局：强制贴图与 R12 原版相比，234 帧全部相同（含 54 帧菜单、面板画面和整个准备期） |
| 像素和状态：Node 整局回归（9,000 帧，有菜单开关） | 强制贴图、真实检测两种跑法，都和 R12 原版一致：150 个逐秒状态、403 帧整屏像素全部相同 |
| 显卡画布（WebKit） | 检测判为不启用，贴图 0 次，走的是原版的绘制指令 |

**效果**（WebKit、CPU 画布、确定性模式、同一局 90 秒，有菜单开关）：

| 时段 | 原画法 | 贴图 |
|---|---|---|
| 准备期（第 3–58 秒）每帧平均 | 5.81 ms | 5.13 ms（−12%） |
| 对局中打开升级面板的那几秒 | 4.61 ms | 3.67 ms（−20%） |

- `why: "cpu"`：已启用；
- `"not-slower"`：显卡画布，不启用；
- `"pixels-differ …"`：像素核对没通过，不启用。

## 5. 还没解决的，以及需要你决定的

**1）绘制仍是大头。** CPU 画布模式下，后期混战每帧约 5 ms（M6），按 iPhone 12 估算仍在 12–15 ms 左右，留给发热降频的余量不多。主要构成（M6，CPU 画布）：

| 项目 | 每帧 |
|---|---|
| 城墙被毁救援提示的全屏暗色遮罩（出现时） | 1.5–2.3 ms（T1 之后：CPU 画布下约 0.3 ms） |
| 准备期（每局前 60 秒）全屏浅蓝色 | 约 1.6 ms（T1 之后：CPU 画布下约 0.3 ms） |
| 准备期跳动的倒计时描边文字 | 约 0.1–0.2 ms |
| 建筑层 | 约 0.86 ms |
| 顶部界面 | 约 0.67 ms |
| 地形 | 约 0.33 ms |
| 树/矿层 | 约 0.31 ms |
| 单位和特效合计 | 约 1 ms |

**2）全屏半透明遮罩：已做（11-25 晚，见 4.5）。** 你定的是只在 CPU 画布启用：
- 开机时先检测；
- 显卡画布的手机不启用，画法和原版一样；
- 遮罩显示期间多占约 5.3 MB 内存，用完 3 秒后释放。

还要在 iPhone 上确认两件事：检测结果是不是「CPU 画布」（看法见 4.5 末尾），以及准备期和菜单打开时帧率有没有改善。

**3）L4 会让部分树的像素有轻微差别，要不要保留，你定。** 详见 4.4。两条路：
- **保留 L4（现在的版本）**：第 60 秒恶魔苏醒切镜超过 16.7 ms 的帧从 26 帧降到 0 帧，最长帧从 28 ms 降到 15.9 ms。代价是切镜之后部分树的像素有轻微差别，肉眼看不出，玩法不变。
- **去掉 L4**：画面和原版逐帧一致，但切镜时的连续长帧会回来。去掉很简单：`art163/terrain-edge-prefetch.js` 换回原版即可，其他改动不受影响。

**4）更快的那种镜头移动仍会顿一下。** 原因是地形缓存只有 16 MB（约 59 块），容不下「出发点一屏 + 路上 + 目的地」，飞回时只能现画。两条路：
- 镜头场景期间临时多给地形缓存约 8 MB；
- 把这种镜头放慢一点，但这会改变镜头表现。

都需要你同意。

**5）高性能模式要在手机上确认真的生效。** 你之前的记录是：
- 开高性能：「流畅了」；
- 关掉：「巨卡发烫」。

游戏开局会把实际模式记进诊断记录（`runtime-mode` 事件里的 `highPerformance`）。真机测试时请先确认它是 `true`；如果是 `false` 或空，后面的优化都不顶用。

**6）测试码。** 微信开发者工具的「服务端口」还是关闭状态。这是安全设置，我不会替你打开。可以：
- 你打开「设置 › 安全设置 › 服务端口」，我来出码；
- 或者你在开发者工具里导入 `恶魔与精灵_R12-PF2优化/client`，直接点「预览」。

## 6. 真机验收怎么做

同一台 iPhone 12，同样亮度和电量区间，分别用 R12 原版和 R12-PF2 测：
1. 单人、8 个电脑队友、疯狂难度，各玩 30 分钟。
2. 记录左上角 FPS、明显顿卡的时间点、机身温度、耗电。
3. 记录内存警告次数（诊断记录里的 `memory` 事件）。
4. 重点看第 60 秒恶魔苏醒切镜，以及第 15 波以后小恶魔围攻城墙的时段。

没在真机上测过的指标，我不会说已经达标。
