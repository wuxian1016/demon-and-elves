# 导入、构建、验收、发布

## 1. 导入与来源核对

1. 从**私有交接链接**获取压缩包，先核验发送方提供的 ZIP SHA-256，再解压至新目录（切勿覆盖原 Mac 工程）。检查 `BUILD-INDEX` 的 build label、相对路径、提交/父 SHA、文件数、文件清单 SHA、冻结日期、承诺范围、测试回执、已知缺项。待补的列为「未知」，不依据文件修改时间猜版本。
2. 在 `latest/client/` 按来源的清单校验 `shasum -a 256 -c 路径/到/source.sha256`；先验证清单文件摘要本身。对于同一棵树比较，区分文件集合变化与内容变化；`.DS_Store`、打包临时文件、绝对路径、微信/OAuth 凭据、本机工作缓存不进清单或 ZIP。保留单一版本基线；有实验补丁或复原分支应分目录，与可编译主树隔开。
3. 在微信开发者工具 import `latest/client/`，小游戏项目，核对 AppID `wxe6064709895531ce`。以这台机器的官方工具版本按已有授权账号登录；没有授权则停在本地。不要把公开网页游戏的演示或 staging 工程误设为此 AppID。项目需要在 `project.config.json` 下识别 `compileType: game`，`game.json` 的实际分包目录要都在，不主动改 iOS 模式。
4. 单人 QA 用临时模拟目录和独立无存档测试机。用真实自然入口而非 fixture 截屏作为最终验收。只有工程明确允许的临时新局才进入，退局明确选择不保存，规避别人正在玩的局、设备设置与权限。

## 2. 复现最小路径

- **冷启动**：关闭本游戏试验窗口再由精确新码打开；手持设备无需开发端账号密钥。确认摄取的是本次图像和新运行标签，不看旧码标题，不批量点屏。开发者工具编译、扫码域名/二维码 SHA 都不能保证手机实际读到版本。曾经出现旧 S2E 码扫描有效却启动更新的 COW3A，同一 AppID 的诊断不要并发轮换。
- **开局**：首页 → 选择本来默认的普通单人中等＋8 电脑 → 开始新局 → 第一有效渲染帧 → 实际轻移与采矿（看到资源变化）→ 打开建造栏、关闭后控制仍有效 → 不保存退出。禁止点击「回档」或篡改用户数据。切后台验证要捕获相同时间/位置/单位/资源并能操作，不把重启首页算继续。
- **技能与卡牌**：横竖屏各跑普通与幽灵真实解锁，首次介绍、跳过、换人/上下车、附身蝙蝠拿货/交付、读旧档和未看过/看过边界。石头真击杀次数、所获可见卡及实际消费效果一并记录，不能只检阅资源文件存在。
- **画质性能**：记录版本、机型、iOS/微信版本、屏幕方向、冷/暖、单人或联机、难度、电脑个数、波次、持续长度。看原始连贯走动、攻击、首次建造、快速拉镜头、多路满怪、告警前后和前后台。至少记录帧时间分布、长帧和崩溃阶段；单帧 FPS 60 不是恒定 60、不发热或满局稳定的证据。
- **本地复用**：随包真有 `qa/` 时才执行并阅读文件入参。例如附带 COW8D CJS fixtures 在实际 runtime/Canvas 宿主里测试入参，不模拟真实广告网络：
  ```sh
  node qa/icon-proof.cjs client portrait /tmp/icons-portrait.json
  node qa/icon-proof.cjs client landscape /tmp/icons-landscape.json
  node qa/stone-proof.cjs client
  node --test qa/ads.test.cjs
  ```
  没包含这些文件时要重建数据/测试，不把示例命令当已跑通。广告用例会读取同层 `../client` 对应配置，测试前确认它正是要验的冻结树。依赖缺少时安装在新的测试环境；不要把测试包管理器缓存或 `node_modules` 带入微信包。需要 Canvas 的 fixtures 按各自依赖声明安装，不用 jsdom 的绘制结果冒充实机。
- **支持资料**：看旧官方回执最好同时看持久源码 SHA 和分析脚本。已知 COW8C SDK 实测主包 4,151,634 B、总包 31,288,073 B，可用于预算参照，不是对其他版本平台尺寸的保证；生产前看当前官方工具实际报告。压缩后要检原尺寸、真实像素、帧数和兼容性，不为了字节偷偷降低画质。

## 3. 官方测试码与正式动作

1. 冻结唯一候选，先做回归、审新旧点和包体，不让并发工具覆盖同 AppID 的当前代码。启动版本标签用不可混淆的标记；记录 CLI 实际版本、AppID、项目源码清单、打包输出和时间。
2. **测试预览**由微信官方 DevTools 当前 CLI/GUI 的预览功能产生。用这台电脑的 `cli --help` 核实选项与登录状态，要求确切 `--project` 路径、实际 QR 原图与打包 JSON 输出。避免同一项目多次同时预览；保留前后实际文件清单相同的证据。核对 SDK 成功、原始 JPG 像素、官方 HTTPS 微信域、二维码独立解码、版本是否新。不要改图后仍声称原始二维码；不把短期 QR 放公开仓库。
3. 收到真实扫码问题时优先核对测试机上的实际版本，区分微信登录/限权、旧版回落、实测错误与代码故障。能通过已授权的私人设备/已确认传递路径测试时，只处理当前已授权图，不索要口令、改权限或使用别人存档。
4. **体验、开发上传、审核和正式发布是不同操作**。本交接本身不创建新预览、不授权新的生产发布、GitHub 写入、后端资源变化、成本或邀请；按实际账号权限、用户约定和项目策略分别处理。若配置不了真广告，只做本地受控回调，不铺生产占位广告位，也不要说用户端广告正常。
5. **私有 GitHub `whxh1987-design/demon-and-elves`**：先核对访问账号与仓库可见性，如果存在新冻结提交，把清单/补丁/QA 关联到确切 hash，保持回滚分支和最小合并。无证据不用私人工作树或历史 R96 代替当前代码，勿 force push/自动删除他人分支。
6. **微信云托管**：单机测试前端不是部署后端。仅当取得独立的后端冻结清单、协议/客户端兼容证据、目标环境、卫生检查和回滚点，才考虑针对性部署。先测试房间协议兼容、冷启动、socket 心跳、快照下发、响应与重连；后台邀请码/账号等只存本机密钥服务。此交接未核实新的现网后端，不填未经验证的地址或部署号。

## 4. 新问题交接格式

每条使用「用户原要求/确认时间 → 受影响模块或原素材 → 可复现步骤 → 最后真证据 → 已合入 SHA/待做」；修复得出结论后列 ✅ 已通过范围、⭕ 待验范围、❌ 明确未过，不报无根据的百分比。历史对话按用户项目内容可导出范围保留，采用换方向后更晚的用户决定；授权/账户访问与设备权限不要复制到配置。如果发现遗漏，先从原有已批准的资源和 QA 基线复原，不另造同名资产。
